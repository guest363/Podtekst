# Компоненты

Модели и ffmpeg закреплены за сборкой Подтекста. Клиент не проверяет версии в
фоне и не ходит за ними в сеть: он показывает то, что лежит в его манифесте, и
ставит компонент по кнопке. За новыми версиями апстримов следят CI и скрипт
мейнтейнера.

Два файла задают состав сборки:

* `src-tauri/crates/mr-models/models-manifest.json` - модели: файлы, ревизии
  апстримов, размеры, SHA-256, порядок версии;
* `src-tauri/crates/mr-app/components-pins.json` - ffmpeg: версия, источник,
  архив и SHA-256 для каждой платформы.

Пины фиксируют версию компонента и, где апстрим публикует архив с SHA-256, ещё
и байты. Пользователь получает ровно то, что проверено при выпуске.

## Как проверяются компоненты

1. **Монитор.** `./scripts/components.sh monitor` сверяет ревизии из манифеста и
   пины ffmpeg с апстримом и печатает отчёт: что изменилось, где новая версия.
   В CI запускается раз в неделю: при расхождении открывает один issue с меткой
   `dependencies`, при совпадении закрывает его. Ошибки сети не считаются
   совпадением: issue остаётся открытым с пометкой о неполной проверке. Файлы
   монитор не меняет.
2. **Валидация.** `./scripts/components.sh lint` проверяет структуру без сети:
   обязательные поля, формат SHA-256, имена файлов, ссылки на ревизию вместо
   `main`, полный набор пинов ffmpeg. `./scripts/components.sh verify-ffmpeg`
   скачивает пин текущей платформы, сверяет SHA-256, версию, архитектуру и
   кодировщики.
3. **Пины.** Новая версия попадает в файлы сборки руками: ревизия апстрима,
   контрольные суммы, размеры, `order` больше прежнего. Для ffmpeg - версия,
   URL архива и SHA-256 в `components-pins.json`.
4. **Релиз.** `./scripts/components.sh report` собирает линт, монитор и проверку
   ffmpeg в `runs/components/<дата>-<коммит>/report.md`, отчёт прикладывается к
   PR выпуска. Линт входит в CI-гейт. В заметках к релизу есть строка
   «Компоненты»: какие версии моделей и ffmpeg вошли в сборку.

## Политика обновлений

* **Модели приходят с обновлением приложения.** Новый манифест едет внутри
  сборки. Файлы не скачиваются сами: пользователь нажимает «Обновить», старая
  копия заменяется только после проверки размера и SHA-256 нового набора.
* **ffmpeg ставится и обновляется по кнопке.** «Скачать», если утилиты нет,
  «Обновить», если версия или архитектура расходятся с пином, «Переустановить»,
  если файлы на месте, но не запускаются или пара ffmpeg/ffprobe не сходится.
  Копия живёт в папке данных приложения и имеет приоритет над системной.
* **Системный ffmpeg не трогаем.** Если пользователь поставил утилиту сам,
  приложение работает с ней и показывает источник «системный». Обновляет её
  пакетный менеджер.
* **Версии не смешиваются.** Поддерживается одна версия компонента на сборку:
  манифест и пины меняются вместе, старые наборы не остаются доступными.
* **Уведомлений о релизах апстрима нет.** Приложение не узнаёт о новых версиях
  само и не показывает баннеров. Расхождение с апстримом находит монитор.

## Ограничения

* **Linux:** статическая сборка johnvansickle выкладывается без SHA-256, поэтому
  байты архива не пиннятся: проверяются размер, состав (только `ffmpeg` и
  `ffprobe`, без абсолютных путей, `..` и символических ссылок), архитектура и
  версия. Версия сверяется с пином fail-closed: когда JVS выпускает новый
  релиз, установка останавливается с ошибкой «апстрим обновился» до обновления
  пина в `components-pins.json`.
* **macOS:** поддерживается только arm64. Сборка для Intel не выпускается, и
  пин для неё не задан.
* **Android:** ffmpeg не используется. Запись экрана и импорт видео доступны
  только на десктопе.
* **Windows:** архив gyan.dev содержит оба бинарника; версия и архитектура
  проверяются по заголовку PE до установки.
